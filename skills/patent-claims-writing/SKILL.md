# 权利要求书撰写

以资深专利工程师视角，基于技术交底书或技术方案，撰写权利要求书。先确定独立权利要求的保护范围，再通过从属权利要求构建防御纵深。

## 输入要求

接受以下任一形式的输入：

| 输入形式 | 说明 |
|---------|------|
| 技术交底书（文件路径或文本） | 优先使用，信息最完整 |
| 技术方案描述 | 需包含：技术领域、核心问题、技术手段、预期效果 |
| 专利申请文件中的说明书 | 从说明书中提取技术特征 |

若输入信息不足以撰写权利要求（缺少核心技术手段或技术问题），需先补充。

## 输出规则

默认输出 Markdown 格式。当用户明确要求 Word 格式时，在阶段 3 转换为 .docx。

输出目录：`./generated_docs/`

| 文件 | 说明 |
|------|------|
| `权利要求书_[发明名称].md` | 独立权利要求2-3条 + 从属权利要求8-12条，总计≥3000汉字 |

## 撰写工作流

**阶段1：技术特征提取**

1. 从输入中提取：技术领域、要解决的技术问题、核心技术手段（原理+方式+参数）、技术效果
2. 识别必要技术特征（缺一不可）和可选技术特征（可替换/可省略）

**阶段2：权利要求撰写**

**【必须】读取 [references/claims-guide.md](references/claims-guide.md) 了解撰写规范**

1. 撰写独立权利要求（2-3条）
   - 前序部分 + 特征部分，禁止功能性限定
   - 独立权利要求字数控制在200-400字，使用上位概括
   - 多个独立权利要求须满足单一性（共享核心技术特征）
2. 撰写从属权利要求（8-12条）
   - 构建树状引用结构（非平铺），形成防御纵深
   - 逐级细化：上位概念→具体实现、优选参数、附加模块
3. 输出中间产物：`权利要求书_[发明名称].md`

**阶段3：转换为 Word 文档（仅用户要求时执行）**

**触发条件**：仅当用户明确要求 Word 格式时执行此阶段。否则阶段 2 的 .md 即为最终交付物。

**【必须】读取 `docx` Skill 了解 python-docx 基础用法**

将 .md 中间产物转换为 `权利要求书_[发明名称].docx`。格式要求：

| 元素 | 格式要求 |
|------|---------|
| 文档标题（权利要求书） | 居中，黑体二号 |
| 权利要求编号 | 加粗，宋体小四 |
| 权利要求正文 | 宋体小四（12pt），行距1.5倍 |
| 独立/从属权利要求 | 每条单独一段，缩进一致 |

## 核心校验要点

- 独立权利要求是否只包含必要技术特征（自测法则：换掉这个特征，技术问题是否仍能解决？）
- 独立权利要求是否使用了上位概括（未锁死具体算法/型号/参数）
- 从属权利要求是否为树状引用（非全部引用权1的平铺结构）
- 权利要求总数10-15条
- 术语全文一致

## 质量检查

- [ ] 权利要求书 .md 内容完整、格式清晰
- [ ] （如用户要求 docx）.docx 可在 Word/WPS 中正常打开，编号加粗、条款间距合理
- [ ] 独立/从属权利要求格式一致
