# 权利要求审查与修改技能

## 定位

本 Skill 解决的核心问题：**已有的权利要求书存在逻辑错误、形式不规范、保护范围不合理等问题，需要逐条检查并按需修改。**

支持两种子模式，根据用户意图自动切换：

| 模式 | 触发条件 | 输入 | 输出 |
|------|---------|------|------|
| **审查模式** | "检测""审查""审核""是否合理""是否正确" | 权利要求书 + [可选:交底书] | 审查报告（不改文档） |
| **修改模式** | "修改""优化""上位""补充""调整" | 权利要求书 + 修改指令 | 修改后权利要求书 |

## 输入

| 输入类型 | 说明 | 必要性 |
|---------|------|--------|
| 权利要求书 | 待审查/修改的权利要求书全文 | 必需 |
| 交底书/技术方案 | 作为参照依据，用于判断权要是否与技术方案一致 | 可选，强烈建议提供 |
| 修改指令 | 具体的修改要求（修改模式必需） | 修改模式必需 |
| 审查报告 | 上一步审查的结果（可先审查再修改） | 可选 |

## 输出

### 审查模式输出

审查报告（Markdown），包含：

```markdown
# 权利要求审查报告

## 审查概要
- 审查对象：[权利要求书名称/来源]
- 权利要求总数：X 项（独立权利要求 X 项，从属权利要求 X 项）
- 综合评级：[通过 / 需修改 / 需重写]

## 逐条审查结果

### 独立权利要求 1
| 检查维度 | 结果 | 问题说明 |
|---------|------|---------|
| 结构完整性 | ✅/❌ | ... |
| 必要技术特征 | ✅/❌ | ... |
| 用语规范性 | ✅/❌ | ... |
| 技术方案可实施性 | ✅/❌ | ... |
| 说明书支持 | ✅/❌ | ... |

### 从属权利要求 2
...

## 形式问题汇总
| # | 权利要求 | 问题类型 | 问题描述 | 严重程度 |
|---|---------|---------|---------|---------|
| 1 | 权3 | 引用逻辑 | 引用了不存在的权5 | P0 |

## 逻辑问题汇总
| # | 权利要求 | 问题类型 | 问题描述 | 严重程度 |
|---|---------|---------|---------|---------|
| 1 | 权1 | 数据流 | 输入来源未明确 | P1 |

## 修改建议
（如果有问题，给出具体的修改建议）
```

### 修改模式输出

修改后的权利要求书（Markdown），包含：

1. **修改后权利要求书全文**
2. **修改对照表**：列出每处修改的位置、修改前、修改后、修改理由
3. **修改说明**：解释修改的整体思路

## 执行流程

### 阶段 1：准备

1. 读取 `knowledge/review-standards/patent/claims-review.md` — 权利要求书审核的**唯一标准定义**（包含评分维度、问题严重等级映射）
2. 读取 `knowledge/references/claims-drafting-rules.md` — 权利要求撰写常见问题清单（辅助参考）
3. 如有交底书，读取交底书内容作为参照
4. 如有审查报告（先审后改流程），读取审查报告
5. 确定执行模式（审查/修改）

### 阶段 2：审查模式执行

#### 步骤 2.1：按标准逐维度检查

依据 `knowledge/review-standards/patent/claims-review.md` 中定义的四个维度逐项检查：

1. **独立权利要求质量**（必要技术特征完整性、保护范围适当性、功能性限定合规性）
2. **从属权利要求防御纵深**（引用结构合理性、从属权附加特征质量）
3. **形式与逻辑合规性**（单一性、引用关系正确性、术语一致性、编号与格式）
4. **整体策略评估**（权利要求总数、保护层次完整性）

每项按标准中的评分锚定打分。

#### 步骤 2.2：参照检查（如有交底书）

1. 权利要求的技术特征是否与交底书一致
2. 权利要求的保护范围是否超出交底书记载
3. 交底书中的关键实施例是否被权利要求覆盖

#### 步骤 2.3：问题严重等级标注

依据 `claims-review.md` 中的"问题严重等级映射"对每个发现的问题标注 P0/P1/P2：

| 等级 | 对应维度得分 | 典型问题 |
|------|------------|---------|
| **P0** | ≤50 | 缺少必要技术特征、引用不存在的权利要求、核心特征严重缺失 |
| **P1** | 60-79 | 保护范围过窄/过宽、用语模糊、数据流断裂、纯功能性限定 |
| **P2** | 80-89 | 标点不规范、附图标记缺失、表述可更精确 |

#### 步骤 2.4：输出审查报告

### 阶段 3：修改模式执行

#### 步骤 3.1：理解修改指令

分析用户的修改要求，明确修改目标：

| 修改类型 | 典型指令 | 处理方式 |
|---------|---------|---------|
| 术语上位 | "上位XX术语""用更宽泛的概念" | 找到术语→确定上位概念→验证说明书支持 |
| 补充从权 | "补充从权""增加XX维度的保护" | 从说明书提取内容→撰写新从权→验证引用关系 |
| 调整引用 | "权4引用逻辑有问题""调整引用关系" | 分析当前引用→修正→验证完整性 |
| 优化措辞 | "优化表述""去除模糊用语" | 定位问题用语→替换为精确表述 |
| 缩小范围 | "缩小保护范围""增加限定" | 确定增加的技术特征→修改权要→验证说明书支持 |
| 增加独权 | "增加方法侧权利要求""增加设备权要" | 基于现有方案→从不同执行主体撰写→验证单一性 |

#### 步骤 3.2：执行修改

1. 读取原始权利要求书
2. 按修改指令逐项修改
3. 每项修改后检查是否引入新问题（引用关系、术语一致性等）

#### 步骤 3.3：修改后自检

修改完成后执行快速自检：

```
[ ] 修改后的引用关系是否正确
[ ] 是否引入了新的形式问题
[ ] 保护范围变化是否符合用户意图
[ ] 修改是否超出原说明书和权利要求书记载的范围
[ ] 术语使用是否前后一致
```

#### 步骤 3.4：输出修改结果

1. 修改后权利要求书全文
2. 修改对照表
3. 修改说明

## 质量检查

### 审查模式质量标准

| 检查项 | 标准 |
|--------|------|
| 检查覆盖率 | 每项权利要求都被检查到 |
| 问题分级准确性 | P0/P1/P2 分级合理 |
| 问题定位精确性 | 指出具体段落/条款 |
| 建议可操作性 | 每个问题都有具体修改建议 |

### 修改模式质量标准

| 检查项 | 标准 |
|--------|------|
| 修改完整性 | 用户的所有修改指令都被执行 |
| 引用关系正确性 | 修改后引用关系无误 |
| 说明书一致性 | 修改内容不超出说明书 |
| 术语一致性 | 修改后术语使用前后一致 |
